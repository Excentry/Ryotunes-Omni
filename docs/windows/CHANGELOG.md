Registro de evidencia, resultados y hallazgos del port a Windows 11. El [roadmap](ROADMAP.md) conserva solo lo que falta por hacer; aquí queda lo que ya se hizo y cómo se comprobó.

> No es el changelog del producto. Ese es [`CHANGELOG.md`](../../CHANGELOG.md) en la raíz, heredado de Ryotunes. Nada de lo registrado aquí implica soporte, build verificado ni release de Windows; ver los [niveles de evidencia](ROADMAP.md#niveles-de-evidencia).

## Convenciones

## Evidencia por tarea

### Spotify playlist import - Phase 0 feasibility

- Inicio (2026-11-14): @IsaVonxz-type asume la investigación de viabilidad por solicitud explícita del usuario. No se aprueba todavía la implementación del importador ni se modifica W23 de @Excentry.
- Inspección estática: `crates/spotify/src/client.rs` inicializa `stream::Engine` en `Client::new`; `crates/spotify/src/stream.rs` crea un FIFO al construir ese motor. El cliente actual no ofrece una inicialización de solo metadatos independiente del transporte de audio. `crates/spotify/src/auth.rs` solicita permisos de streaming y biblioteca, aplica el gate Premium en `sign_in` y `restore`, y genera un estado OAuth que el callback actual no compara. No se reutilizará ese flujo sin separar autorización y validar el callback.
- Documentación oficial consultada mediante Context7: [quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes), [PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow) y [playlist](https://developer.spotify.com/documentation/web-api/reference/get-playlist). La Web API permite investigar lectura sin inicializar librespot; development mode exige Premium al dueño de la app y cuentas de prueba autorizadas. La documentación de playlist limita la disponibilidad de sus items a playlists propias o en las que el usuario colabora; no se promete importar cualquier playlist seguida.
- Política consultada directamente: [Spotify Developer Policy](https://developer.spotify.com/policy), con vigencia indicada de 2025-05-15. III.9 contempla transferencia de datos personales o metadatos de playlists por el usuario; III.5 restringe integración con streams o contenido de otro servicio. Esa excepción no demuestra autorización para reproducción integrada ni descargas. Se requiere revisión antes de habilitar esos destinos; no es una conclusión legal.
- Siguiente prueba: OAuth PKCE con una app registrada y autorizada para este proyecto, scopes mínimos de biblioteca, perfil aislado y lecturas paginadas. Verificar conteos, orden, repeticiones y entradas no disponibles sin guardar tokens, respuestas de autorización ni datos privados en el repositorio.

### W23 — Spike de transportes Spotify

- Selección actual de Excentry para la medición real: Sink de librespot → canal PCM acotado → TCP loopback → libmpv. El named pipe queda como comparador; libmpv solo pudo abrirlo como medio usando el prefijo extendido `\\?\pipe\`, no la ruta Win32 habitual `\\.\pipe\`.
- La alternativa previamente seleccionada (Sink → canal → protocolo custom libmpv) se abandonó tras un intento de dos opens sucesivos que terminó en `SIGSEGV` en Linux con libmpv2 4.1.0. La inspección de `libmpv2-4.1.0/src/mpv/protocol.rs` sugiere use-after-free de estado registrado por el callback close; no se confirmó con upstream. Se conservó la evidencia histórica en el PR draft #49; no se cambiaron Cargo ni lockfiles. libmpv2 5.0.3 reestructura el wrapper por stream, pero migrarlo cambia la API de eventos de `player` y se dejó fuera de esta selección.

Se usaron tres pistas, TCP y named pipe, y una copia local del fork con reintentos espaciados de 3, 5, 10 y 20 s. No se produjo ningún byte de PCM. Es el problema abierto [librespot-org/librespot#1649](https://github.com/librespot-org/librespot/issues/1649), que otras apps reportan también con cuentas antiguas. Medido: el rechazo. Inferido: que es persistente por cuenta, porque solo se probó una cuenta.
- Spotify Soloist 1.3.10.42 (build 1793793704, 20261104, firma Authenticode válida de Spotify AB): el emparejamiento desde la app de escritorio, la restauración de sesión y `soloist ctl activate` y `play` funcionaron, y el proceso terminó con `0xC0000005` unos 2 s después de empezar a sonar en **5 de 5** intentos. Se probó con las salidas predeterminadas EarPods y Speaker (Realtek), y con Realtek con la app FxSound cerrada. El módulo del fallo es `soloist.exe` en los offsets `0x208539` a `0x210285`; en el primer fallo era un módulo desconocido en `0x0`. Está reportado en [spotify/soloist#28](https://github.com/spotify/soloist/issues/28), donde otra persona reproduce el fallo en la build `26300.9818`. No se identificó la causa. Hay usuarios en Windows 11 25H2 que reportan que funciona, algo que no se midió aquí.
- Descartado: los reintentos y el cambio de transporte, porque el rechazo ocurre antes del Sink; y capturar la salida de Soloist para pasarla por libmpv, porque Music Assistant advierte que los términos de Spotify no lo permiten con claridad.
- Hallazgo del harness: `load` no termina si la pista anterior acabó en `Unavailable`. Se observó un bloqueo; por el código, el Sink pendiente de esa pista no se libera, lo que es una inferencia.
- Los datos de prueba (sesión de Spotify, clave de Soloist y registros con el ID de usuario) quedaron solo en la máquina local y no se adjuntan.
- Reabrir cuando se cumpla alguna de estas condiciones: una cuenta Premium que librespot pueda reproducir en una máquina Windows 11 interactiva, con la que se completan las mediciones TCP y named pipe del #14; una build de Soloist que no se cierre en Windows 26300.x; o un cambio en librespot que resuelva el rechazo de claves.
